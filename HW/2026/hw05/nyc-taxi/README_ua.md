# Конвеєри таксі Нью-Йорка - зразковий проект Bruin

Комплексний конвеєр ELT, створений за допомогою Bruin, який демонструє найкращі практики створення конвеєрів даних. Цей проект обробляє дані про поїздки на таксі в Нью-Йорку з загальнодоступних джерел HTTP, перетворює їх через кілька рівнів і генерує аналітичні звіти.

Конвеєр витягує дані про поїздки на таксі в Нью-Йорку з файлів HTTP parquet, очищає та перетворює їх і генерує щомісячні зведені звіти. Він використовує DuckDB для локальної обробки та дотримується трирівневої архітектури: необроблені (прийом і необроблені) → проміжні (очищені) → звіти (агреговані).

## Чого прагне досягти цей проект

Цей проект служить **шаблоном і навчальним ресурсом** для розробників, які хочуть зрозуміти можливості Bruin і як створювати готові до виробництва конвеєри даних. Він демонструє:

- **Повноцінні робочі процеси ELT**: від прийому необроблених даних до аналітичної звітності
- **Багаторівнева архітектура даних**: реалізація багатошарового підходу (прийом → необроблені → очищені → агреговані)
- **Інкрементна обробка даних**: використання інкрементних стратегій на основі часу для ефективного оновлення даних
- **Якість та трансформація даних**: очищення, збагачення та перевірка якості даних
- **Інтеграція Python та SQL**: поєднання прийому на основі Python з перетвореннями SQL

## Які інструменти та функції Bruin демонструє цей проект

### Основні функції Bruin

1. **Матеріалізація ресурсів Python**
   - Демонструє, як використовувати Python для складного прийому даних
   - Показує інтеграцію з зовнішніми API та джерелами даних HTTP
   - Повертає Pandas DataFrames, які Bruin автоматично матеріалізує в таблиці

2. **Стратегія додавання + дедуплікації**
   - Рівень необроблених даних використовує матеріалізацію `append` для простого та швидкого прийому
   - Проміжний рівень дедуплікує за допомогою `QUALIFY ROW_NUMBER()` для обробки повторно прийнятих даних
   - Зберігає останній витягнутий запис за наявності дублікатів

3. **Інкрементна стратегія часового інтервалу**
   - Ефективна інкрементна обробка з використанням матеріалізації `time_interval`
   - Автоматична обробка діапазону дат та видалення/заміна даних
   - Усічення на рівні місяця для пакетної обробки

4. **Змінні конвеєра**
   - Використання змінних на рівні конвеєра (наприклад, `taxi_types`) для конфігурації
   - Доступ до змінних у ресурсах Python через змінну середовища `BRUIN_VARS`
   - Використання змінних у ресурсах SQL через шаблони Jinja

5. **Походження та залежності даних**
   - Явні оголошення залежностей між ресурсами
   - Автоматичне визначення залежностей та порядок виконання
   - Потік даних між рівнями

6. **Управління метаданими**
   - Вичерпні описи стовпців та документація
   - Визначення первинних ключів та обмеження, що допускають значення NULL

7. **Перевірка якості даних**
   - Спеціальні перевірки якості за допомогою запитів SQL для перевірки бізнес-правил та цілісності даних
   - Перевірки на рівні стовпців за допомогою вбудованих типів перевірок (невід’ємні, позитивні, мінімальні, максимальні)

## Шлях навчання

1. Почніть з `trips_raw.py`, щоб зрозуміти матеріалізацію ресурсів Python зі стратегією додавання
2. Перегляньте `taxi_zone_lookup.sql` та `payment_lookup.asset.yml`, щоб побачити різні шаблони довідкових таблиць
3. Перегляньте `trips_summary.sql` для нормалізації стовпців, збагачення та шаблонів дедуплікації
4. Вивчіть `report_trips_monthly.sql` для технік агрегації
5. Дослідіть `pipeline.yml`, щоб зрозуміти конфігурацію та змінні

## Джерело даних

Цей проект використовує загальнодоступні дані про поїздки на таксі в Нью-Йорку з [NYC TLC Trip Record Data](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page). Дані доступні через кінцеві точки HTTP, які надають історичну інформацію про поїздки на таксі в Нью-Йорку у форматі parquet.

## Конфігурації з'єднань (`.bruin.yml`)

Перед запуском конвеєра вам потрібно створити файл `.bruin.yml` у кореневому каталозі проекту, щоб [налаштувати локальне з'єднання DuckDB](https://getbruin.com/docs/bruin/platforms/duckdb.html). У цьому файлі ви налаштовуєте будь-яке з'єднання з базою даних, а також [спеціальні секрети](https://getbruin.com/docs/bruin/secrets/bruinyml.html#bruin-yml-schema).

Файл `.bruin.yml` налаштовує ваше локальне середовище розробки та повідомляє Bruin, де створювати та зберігати файл бази даних DuckDB. Якщо файл бази даних duckdb ще не існує, він буде автоматично створений при першому запуску конвеєра.

**Створіть файл `.bruin.yml`** у кореневому каталозі проекту:
   ```yaml
   default_environment: default
   environments:
       default:
           connections:
               duckdb:
                   - name: duckdb-default
                     path: duckdb.db
   ```

Зверніть увагу, що найкращою практикою є додавання `.bruin.yml` до вашого файлу `.gitignore`, оскільки:
   - Він може містити конфіденційну інформацію про з'єднання та облікові дані автентифікації
   - Різні розробники можуть мати різні шляхи до локальної бази даних
   - Конфігурації для конкретного середовища не повинні бути зафіксовані в системі контролю версій

## Конфігурація конвеєра (`pipeline.yml`)

```yaml
name: nyc-taxi-pipelines
schedule: monthly
start_date: "2022-01-01"
default_connections:
  duckdb: "duckdb-default"
variables:
  taxi_types:
    type: array
    items:
      type: string
    default: ["yellow", "green"]
```

### Розділи конфігурації

#### `start_date`
`start_date` визначає найранішу дату для обробки даних. Коли запускається повне оновлення, початок інтервалу автоматично встановлюється на цю `start_date`, і конвеєр прийматиме та оброблятиме всі дані, починаючи з цієї дати. Це корисно для:
- Встановлення базової лінії для заповнення історичних даних
- Обмеження обсягу операцій повного оновлення, щоб уникнути обробки надзвичайно великих діапазонів дат
- Визначення найранішої точки в часі, яку ваш конвеєр повинен враховувати

#### `default_connections`
Цей розділ ініціалізує з'єднання з базою даних, які будуть використовуватися в усьому конвеєрі. У цьому випадку він ініціалізує екземпляр DuckDB і надає курсор з'єднання з назвою `duckdb-default`, на який можуть посилатися ресурси. Назва з'єднання (`duckdb-default`) повинна відповідати назві з'єднання, зазначеній у вашому файлі `.bruin.yml`.

#### `variables`
Спеціальні змінні на рівні конвеєра дозволяють налаштовувати багаторазові значення, до яких можна отримати доступ у всіх ресурсах конвеєра. Змінні можуть бути:
- **Використані в ресурсах Python**: доступні через змінну середовища `BRUIN_VARS` (аналізуються як JSON)
- **Використані в ресурсах SQL**: посилання за допомогою синтаксису шаблонів Jinja (наприклад, `{{ taxi_types }}`)
- **Перевизначені під час виконання**: передаються через аргументи командного рядка під час запуску конвеєра

У цьому конвеєрі змінна `taxi_types` дозволяє налаштовувати, які типи таксі приймати (жовті, зелені або обидва) без зміни коду ресурсу.

## Специфікації ресурсів

### Іменування ресурсів

Параметр `name` у конфігураціях ресурсів Bruin (наприклад, `name: raw.trips_raw`) є **необов’язковим**. Якщо його не вказано, Bruin автоматично виводить назву ресурсу з шляху до файлу:
- Назва батьківської папки стає назвою схеми/набору даних (наприклад, `raw`)
- Назва файлу (без розширення) стає назвою ресурсу (наприклад, `trips_raw.py` → `trips_raw`)
- У сукупності це створює повну назву ресурсу: `raw.trips_raw`

**Приклад**: Файл за адресою `assets/raw/trips_raw.py` буде автоматично названий `raw.trips_raw` навіть без явного параметра `name` у конфігурації ресурсу.

Ви все ще можете явно вказати параметр `name`, якщо хочете перевизначити цю поведінку за замовчуванням або якщо структура вашого файлу не відповідає бажаній конвенції іменування.

### 1. Raw: Прийом та зберігання необроблених даних

#### `raw.trips_raw`
- **Тип**: `python`
- **Стратегія**: `append`
- **З'єднання**: `duckdb-default`
- **Призначення**: Прийом необроблених даних про поїздки з файлів HTTP parquet за допомогою Python

**Огляд матеріалізації Python**:
Матеріалізація Python від Bruin дозволяє писати код Python, який повертає Pandas DataFrame, який Bruin автоматично матеріалізує в таблицю бази даних. Цей підхід є вигідним, оскільки:
- **Немає ручних операцій з базою даних**: Вам не потрібно безпосередньо використовувати бібліотеку Python від DuckDB або писати SQL для створення/вставки даних
- **Автоматична обробка схеми**: Bruin виводить схему з вашого DataFrame і відповідно створює таблицю
- **Відповідність ресурсам SQL**: На матеріалізовану таблицю можна посилатися за допомогою ресурсів SQL так само, як і на будь-яку іншу таблицю
- **Спрощена обробка даних**: Ви можете зосередитися на логіці вилучення та перетворення даних, не турбуючись про управління з'єднаннями з базою даних

Функція `materialize()` є обов'язковою і повинна повертати Pandas DataFrame. Bruin викликає цю функцію, отримує DataFrame і обробляє всі операції з базою даних для зберігання її як таблиці на основі стратегії матеріалізації.

**Конфігурація Bruin**:
- Зберігає вихідні назви стовпців з файлів parquet як є (наприклад, `tpep_pickup_datetime` для жовтих таксі, `lpep_pickup_datetime` для зелених таксі, `pulocationid` тощо)
- Нормалізація стовпців (COALESCE для стовпців datetime, перейменування) відбувається на проміжному рівні, а не в необроблених даних
- Додає стовпець `taxi_type` зі змінних конвеєра
- Додає стовпець мітки часу `extracted_at`
- Використовує стратегію `append`—дедуплікація обробляється нижче за течією в `staging.trips_summary`
- Залежності Python визначені в `requirements.txt` у корені конвеєра

**Вибір дизайну - Чому Python з додаванням?**:
- **Python для складного прийому**: Python ідеально підходить для цього випадку використання, оскільки він дозволяє нам динамічно перебирати діапазони дат та типи таксі за допомогою змінних Bruin (`BRUIN_START_DATE`, `BRUIN_END_DATE` та `BRUIN_VARS`). Це забезпечує гнучку логіку прийому, яка може обробляти кілька джерел та діапазонів дат без жорсткого кодування значень.
- **Стратегія `append`**: Стратегія додавання просто додає нові записи до таблиці. Якщо той самий діапазон дат буде повторно прийнятий (наприклад, запуск конвеєра двічі для січня 2025 року), на рівні необроблених даних будуть створені дублікати. Ці дублікати обробляються на проміжному рівні за допомогою дедуплікації `QUALIFY ROW_NUMBER()`.
- **Матеріалізація Python від Bruin**: Використання функції матеріалізації Python від Bruin усуває необхідність ручних операцій з базою даних. Ми просто повертаємо Pandas DataFrame, і Bruin автоматично обробляє все управління з'єднаннями з базою даних, виведення схеми та створення/вставку таблиць. Це дозволяє коду зосередитись на логіці вилучення та перетворення даних.

#### `raw.taxi_zone_lookup`
- **Тип**: `duckdb.sql`
- **Стратегія**: `create+replace` (неявно - стратегія не вказана, таблиця замінюється при кожному запуску)
- **Призначення**: Завантаження довідкової таблиці зон таксі з джерела HTTP CSV

**Конфігурація Bruin**:
- Первинний ключ: `location_id` (не може бути NULL)
- Використовує функцію `read_csv()` від DuckDB з `header=true` та `auto_detect=true` і передає URL-адресу HTTP, яка містить файл CSV
- Фільтрує NULL `location_id`, щоб забезпечити якість даних
- Стратегія: Таблиця замінюється при кожному запуску, щоб забезпечити наявність найновішої інформації про зони

**Вибір дизайну**:
- DuckDB має вбудовані функції прийому; коли URL-адреса надається з функцією `read_csv`, вона по суті завантажує файл CSV і створює таблицю
- Довідкова таблиця може оновлюватися NYC TLC (нові зони, перейменовані зони тощо) - створення/заміна забезпечує, що ми завжди маємо найновішу інформацію про зони

#### `raw.payment_lookup`
- **Тип**: `duckdb.seed`
- **Призначення**: Завантаження довідкової таблиці типів платежів з локального вихідного файлу CSV

**Конфігурація Bruin**:
- Первинний ключ: `payment_type_id` (не може бути NULL)
- Читає з локального файлу CSV: `payment_lookup.csv`
- Зіставляє коди типів платежів (0-6) з описом, що читається людиною

**Вибір дизайну - Чому ресурс насіння DuckDB?**:
- **Статичні довідкові дані**: Коди типів платежів стандартизовані та не змінюються часто (на відміну від зон таксі, які можуть оновлюватися NYC TLC)
- **Контроль версій**: Локальний вихідний файл забезпечує контроль версій та відтворюваність - зіставлення типів платежів є частиною кодової бази конвеєра
- **Простота**: Ресурси насіння - це зручний спосіб завантаження статичних даних у базу даних без написання запитів SQL
- **Автоматична матеріалізація**: Ресурси насіння автоматично матеріалізуються в таблицю при кожному запуску, подібно до ресурсів SQL, але з меншою кількістю шаблонного коду
- **Немає зовнішніх залежностей**: На відміну від `taxi_zone_lookup`, який залежить від зовнішнього джерела HTTP, ця довідкова таблиця є самодостатньою в межах конвеєра

**Коли використовувати ресурси насіння проти ресурсів SQL**:
- Використовуйте **ресурси насіння** для статичних довідкових даних, які рідко змінюються і повинні контролюватися версіями
- Використовуйте **ресурси SQL** (наприклад, `taxi_zone_lookup`) для даних, які можуть часто змінюватися або надходять із зовнішніх джерел

### 2. Staging: Очищені та збагачені дані

#### `staging.trips_summary`
- **Тип**: `duckdb.sql`
- **Стратегія**: `time_interval`
- **Інкрементний ключ**: `pickup_time`
- **Гранулярність часу**: `timestamp`
- **Первинний ключ**: Складений (`pickup_time`, `dropoff_time`, `pickup_location_id`, `dropoff_location_id`, `taxi_type`)
- **Призначення**: Нормалізація назв стовпців, очищення та збагачення даних про поїздки

**Стратегія часового інтервалу**:
Стратегія `time_interval` призначена для інкрементної обробки на основі ключів на основі часу. Як це працює:
- Bruin автоматично обчислює діапазон дат на основі параметрів запуску (`start_datetime` та `end_datetime`)
- Він видаляє всі рядки в цільовій таблиці, де `incremental_key` (pickup_time) потрапляє в цей діапазон дат
- Потім він вставляє нові дані з результатів запиту для того самого діапазону дат
- Це забезпечує ефективне оновлення: обробляється лише відповідний період часу, а не вся таблиця

Чому ми її обрали: Ця стратегія ідеально підходить для даних часових рядів, де ми хочемо повторно обробити певні діапазони дат (наприклад, для обробки даних, що надійшли із запізненням, або виправлень), не впливаючи на інші періоди часу.

**Конфігурація Bruin**:
- Читає з `raw.trips_raw`
- Нормалізує назви стовпців за допомогою COALESCE для обробки типів таксі жовтого (tpep_*) та зеленого (lpep_*):
  - `COALESCE(tpep_pickup_datetime, lpep_pickup_datetime)` → `pickup_time` (приведено до TIMESTAMP)
  - `COALESCE(tpep_dropoff_datetime, lpep_dropoff_datetime)` → `dropoff_time` (приведено до TIMESTAMP)
  - `pulocationid` → `pickup_location_id`
  - `dolocationid` → `dropoff_location_id`
  - `payment_type` → приведено до INTEGER
- Обчислює `trip_duration_seconds` з часу посадки та висадки
- Збагачує даними про місцезнаходження з `raw.taxi_zone_lookup`
- Збагачує описами типів платежів з `raw.payment_lookup`
- Застосовує фільтри якості даних (позитивна тривалість, розумна довжина поїздки, невід’ємні суми, дійсні типи платежів)
- **Дедуплікує записи** за допомогою `QUALIFY ROW_NUMBER()`, розділеного за атрибутами поїздки (див. Стратегію дедуплікації нижче)
- Додає стовпець мітки часу `updated_at`
- Зберігає мітку часу `extracted_at` з необроблених даних
- Усі стовпці первинного ключа не можуть бути NULL

**Стратегія дедуплікації**:

Оскільки `raw.trips_raw` використовує стратегію матеріалізації **append**, повторне прийняття того самого діапазону дат (наприклад, запуск конвеєра двічі для січня 2025 року) створює дублікати записів. Тому дедуплікація обробляється на цьому проміжному рівні за допомогою `QUALIFY ROW_NUMBER()`.

Логіка дедуплікації розділяє за цими стовпцями та зберігає останній витягнутий запис (`ORDER BY extracted_at DESC`):
- `pickup_time`, `dropoff_time`
- `pickup_location_id`, `dropoff_location_id`
- `taxi_type`, `trip_distance`, `passenger_count`
- `fare_amount`, `tip_amount`, `total_amount`, `payment_type`

**Чому ця комбінація?** Набір даних NYC TLC не має єдиного унікального ідентифікатора поїздки. Однак ймовірність виникнення двох абсолютно однакових поїздок (однаковий час посадки/висадки, місцезнаходження, відстань, кількість пасажирів та деталі оплати) фактично дорівнює нулю. Ця комбінація стовпців надійно ідентифікує унікальні поїздки.

### 3. Reports: Агрегована аналітика

#### `reports.report_trips_monthly`
- **Тип**: `duckdb.sql`
- **Стратегія**: `time_interval`
- **Інкрементний ключ**: `month_date`
- **Гранулярність часу**: `timestamp`
- **Первинний ключ**: Складений (`taxi_type`, `month_date`)
- **Призначення**: Створення щомісячних зведених звітів

**Стратегія часового інтервалу**:
Використовує `month_date` як інкрементний ключ, який є першим днем кожного місяця. Це дозволяє повторно обробляти певні місяці (наприклад, якщо вихідні дані виправлені), не впливаючи на інші місяці.

**Конфігурація Bruin**:
- Читає з `staging.trips_summary`
- Агрегує дані за `taxi_type` та місяцем
- Додає стовпець мітки часу `updated_at`
- Агрегує `extracted_at` за допомогою MAX для відстеження останнього часу вилучення за місяць

## Тестування та запуск конвеєра

Перед запуском перевірте конфігурацію конвеєра:

```bash
bruin validate ./nyc-taxi/pipeline.yml --environment default
```

### Крок 1: Тестування окремих ресурсів

Перед запуском повного конвеєра рекомендується протестувати окремі ресурси, щоб переконатися, що вони працюють правильно. Ви можете запустити один ресурс, вказавши шлях до файлу ресурсу:

```bash
# Приклад: Тестування ресурсу прийому Python
bruin run ./nyc-taxi/assets/raw/trips_raw.py \
  --start-date 2021-01-01 \
  --end-date 2021-01-31 \
  --environment default
```

Ви також можете протестувати з одним типом таксі, перевизначивши змінну `taxi_types`:

```bash
# Тестування тільки з жовтими таксі
bruin run ./nyc-taxi/assets/raw/trips_raw.py \
  --start-date 2021-01-01 \
  --end-date 2021-01-31 \
  --environment default \
  --var 'taxi_types=["yellow"]'

# Тестування тільки з зеленими таксі
bruin run ./nyc-taxi/assets/raw/trips_raw.py \
  --start-date 2021-01-01 \
  --end-date 2021-01-31 \
  --environment default \
  --var 'taxi_types=["green"]'
```

При запуску одного ресурсу виконується лише цей ресурс. Щоб також запустити всі наступні ресурси (ресурси, які залежать від того, який ви запускаєте), додайте прапор `--downstream`:

```bash
bruin run ./nyc-taxi/assets/raw/trips_raw.py \
  --start-date 2021-01-01 \
  --end-date 2021-01-31 \
  --environment default \
  --downstream
```

### Крок 2: Запуск повного конвеєра

Щоб запустити весь конвеєр, вкажіть шлях до `pipeline.yml`:

```bash
# Інкрементний запуск (за замовчуванням)
bruin run ./nyc-taxi/pipeline.yml \
  --start-date 2021-01-01 \
  --end-date 2022-02-28 \
  --environment default
```

**Інкрементний проти повного оновлення:**

- **Інкрементний (за замовчуванням)**: Обробляє лише вказаний діапазон дат. Використовує прапори `--start-date` та `--end-date`, які ви надаєте.
- **Повне оновлення**: Повторно обробляє всі дані з `start_date` конвеєра (визначеного в `pipeline.yml`) до `--end-date`, який ви вказуєте. Повні оновлення також відтворюють усі таблиці в базі даних замість запуску інкрементного запиту.

```bash
# Запуск повного оновлення (повторна обробка з дати початку конвеєра до кінцевої дати)
bruin run ./nyc-taxi/pipeline.yml \
  --end-date 2022-02-28 \
  --full-refresh \
  --environment default
```

**Запуск конвеєра проти одного ресурсу + наступних:**

- **Запуск конвеєра** (`bruin run ./pipeline.yml`): Виконує всі ресурси в конвеєрі в порядку залежностей, дотримуючись вказаного вами діапазону дат.
- **Запуск одного ресурсу з `--downstream`**: Виконує лише цей ресурс та його наступні залежності. Це корисно, коли ви хочете протестувати певну частину конвеєра, не запускаючи все.

**Розширення VS Code:**

Ви також можете запускати конвеєри та ресурси безпосередньо з розширення Bruin VS Code. Відкрийте будь-який файл ресурсу або `pipeline.yml` і відкрийте інтерфейс панелі Bruin (натисніть логотип Bruin у верхній частині відкритого файлу). Будь ласка, зверніться до сторінки розширення Bruin VS Code для отримання додаткової інформації.

## Перевірка даних

### Використання `bruin query`

Команда `bruin query` дозволяє виконувати запити SQL до ваших з'єднань з базою даних. Ви можете робити запити за назвою з'єднання:

```bash
# Запит за назвою з'єднання
bruin query --connection duckdb-default --query "SELECT COUNT(*) FROM raw.trips_raw"
```

**Приклади запитів:**

```bash
# Перевірка щомісячного звіту (повинно показати 14 місяців для 2021-01 по 2022-02)
bruin query --connection duckdb-default --query "SELECT COUNT(*) as month_count FROM reports.report_trips_monthly WHERE month_date >= '2021-01-01' AND month_date <= '2022-02-28'"

# Перевірка деталей щомісячного звіту
bruin query --connection duckdb-default --query "SELECT * FROM reports.report_trips_monthly WHERE month_date >= '2021-01-01' AND month_date <= '2022-02-28' ORDER BY month_date"
```

### Використання DuckDB CLI

Ви також можете робити запити до вашої бази даних DuckDB безпосередньо за допомогою інструменту командного рядка DuckDB. Файл бази даних знаходиться за адресою `duckdb.db` (як зазначено у вашому `.bruin.yml`):

```bash
# Запуск запитів у терміналі
duckdb duckdb.db -c "SELECT COUNT(*) FROM raw.trips_raw"

# Відкриття інтерактивної оболонки DuckDB
duckdb duckdb.db

# Запуск веб-інтерфейсу DuckDB (інтерфейс localhost)
duckdb duckdb.db -ui
```

Прапор `-ui` відкриває веб-інтерфейс у вашому браузері, де ви можете виконувати запити, досліджувати таблиці та інтерактивно візуалізувати дані.

## Ключові деталі реалізації

1. **Діапазон дат до місяців**:
   - Читання дат зі змінних середовища `BRUIN_START_DATE` та `BRUIN_END_DATE` (формат РРРР-ММ-ДД)
   - Використання функції `generate_month_range()` для перетворення діапазону дат у список кортежів (рік, місяць)
   - Правильно обробляє діапазони, що охоплюють кілька років (наприклад, 2021-12-01 до 2022-01-01 → грудень 2021, січень 2022)
2. **Дедуплікація на проміжному рівні**:
   - Рівень прийому (`raw.trips_raw`) використовує стратегію **append**, що означає, що повторне прийняття того самого діапазону дат створює дублікати. Дедуплікація обробляється в `staging.trips_summary` за допомогою `QUALIFY ROW_NUMBER()`.
   - Згідно з [документацією NYC TLC](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page), немає єдиного унікального ідентифікатора поїздки. Однак комбінація атрибутів поїздки (час посадки/висадки, місцезнаходження, відстань, кількість пасажирів, деталі оплати) надійно ідентифікує унікальні поїздки—ймовірність двох абсолютно однакових поїздок фактично дорівнює нулю.
   - Дедуплікація зберігає останній витягнутий запис за наявності дублікатів (`ORDER BY extracted_at DESC`).
3. **Нормалізація стовпців**:
   - **Рівень прийому (raw.trips_raw)**: Зберігає вихідні назви стовпців з файлів parquet як є (наприклад, `vendorid`, `tpep_pickup_datetime` для жовтих таксі, `lpep_pickup_datetime` для зелених таксі, `pulocationid`). Додає стовпці `taxi_type` та `extracted_at`.
   - **Проміжний рівень (staging.trips_summary)**: Перетворює назви стовпців у більш читабельні, узгоджені формати:
     - Використовує `COALESCE(tpep_pickup_datetime, lpep_pickup_datetime)` → `pickup_time` (приведено до TIMESTAMP) для обробки обох типів таксі
     - Використовує `COALESCE(tpep_dropoff_datetime, lpep_dropoff_datetime)` → `dropoff_time` (приведено до TIMESTAMP)
     - `pulocationid` → `pickup_location_id`
     - `dolocationid` → `dropoff_location_id`
     - `payment_type` → приведено до INTEGER
   - Це розділення дозволяє рівню прийому обробляти дані як є, тоді як проміжний рівень стандартизує схему для подальшого споживання
4. **Типи таксі**: Налаштовуються за допомогою змінних конвеєра (за замовчуванням: `["yellow", "green"]`), доступні в ресурсах Python через змінну середовища `BRUIN_VARS`
5. **З'єднання з довідковими таблицями**: Використовуйте `LEFT JOIN` для збереження всіх поїздок, навіть якщо `location_id` або `payment_type_id` не знайдені в довідкових таблицях (taxi_zone_lookup та payment_lookup)
6. **Відстеження міток часу**:
   - `extracted_at`: Встановлюється на рівні прийому під час завантаження даних
   - `updated_at`: Встановлюється на проміжному рівні та в звітах під час оновлення/оновлення даних
